# Research: Hardening and Release Readiness

All findings below come from reading the current code on `main` (features 001–011 merged) and the constitution. No `NEEDS CLARIFICATION` items remain; spec-level decisions were settled in `/speckit-clarify` (migrations, health exposure, proxies, storage persistence, recovery delivery).

## Current-state audit (what exists today)

| Area | Finding |
|------|---------|
| Health | `GET /health/live` returns 204 and touches nothing external. **No readiness endpoint.** |
| Config files | **No `appsettings*.json` tracked.** Logging levels are framework defaults (EF Core logs SQL text at Information). |
| Config validation | Scattered eager checks inside `AddInfrastructure` / `AddApiServices` (DB connection, session lifetimes, signing key, profile images, admin list, audit retention, request body limit). ## Decisions

### R1 — One "Production-class" environment rule
- **Decision**: An environment is *Production-class* unless it is `Development` or `Testing`. All unsafe-default gating (signing key, recovery adapter, storage root, persistence declaration, HSTS, proxy warnings) uses one extension method, replacing the ad-hoc `IsDevelopment()` / `Development||Testing` mix. Staging-like names are therefore treated as Production (secure by default).
- **Rationale**: FR-018/019. Removes the inconsistent Testing-gets-HSTS case and makes safe the default for any unknown environment name.
- **Signing key exception**: an ephemeral signing key is allowed **only in `Development`** (existing behavior, stricter than the class rule); `Testing` must supply a key.
- **Alternatives**: Match literal `"Production"` only — rejected: a typo or `Staging` would silently get development conveniences.

### R2 — Typed, fail-fast configuration validation without a new framework
- **Decision**: (a) Introduce `StartupConfigurationException(setting, reason)` carrying only a setting key and a value-free reason; existing eager loaders throw it with the key named. (b) New per-area options classes with built-in `IValidateOptions<T>` + `ValidateOnStart()` for the areas that lack validation (rate limits, forwarded headers, profile persistence declaration, data protection). (c) The entry point separates *build* and *start* phases, catches `StartupConfigurationException` / `OptionsValidationException` only during startup, writes one structured Critical log naming the setting(s), and exits non-zero **without a stack trace**.
- **Rationale**: FR-014–016, SC-004. Native .NET options validation is sufficient; no generic framework (spec). Aggregation is automatic for options validators; eager loaders fail on first error, which is acceptable and still names the setting.
- **Alternatives**: A custom aggregate validator replacing all loaders — rejected as larger churn on 011 code for little benefit.

### R3 — Forwarded headers: explicit trusted proxies only; beware the env-var trap
- **Decision**: New config `ForwardedHeaders:KnownProxies` (IP list) and `ForwardedHeaders:KnownNetworks` (CIDR list). If both are empty the forwarded-header middleware is **not added** (direct-deployment behavior) and a startup warning is logged (clarification Q3). If present: `XForwardedFor | XForwardedProto` only (never `XForwardedHost`), `ForwardLimit = 1`, default known-proxy/network lists cleared then replaced by the configured ones. Validation rejects unparsable entries and any network that trusts any source (`0.0.0.0/0`, `::/0`). Middleware is the first in the pipeline, ahead of HSTS, HTTPS redirection and rate limiting, so partitions use the real client address.
- **Trap**: ASP.NET Core's container support honors `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true`, which trusts all proxies. The image and compose file MUST NOT set it, and documentation tells operators not to; startup validation fails if that variable is truthy while no explicit trust list is configured.
- **Alternatives**: Always trust the first hop — rejected (spoofable); require a declaration of "no proxy" — rejected in Q3.

### R4 — Migration mechanism: `migrate` subcommand of the API image + idempotent SQL from the same build
- **Decision**: `dotnet GaussAuth.Api.dll migrate` runs a **minimal separate host** that registers only the DbContext (needs only the connection string, not signing keys or storage), applies pending migrations via `Database.MigrateAsync`, logs each applied migration name, and returns exit code 0 on success / non-zero on failure with a value-free diagnostic naming the failing migration. The web host never calls `Migrate`. The Docker **build stage** also runs `dotnet ef migrations script --idempotent` and copies the result to `/app/db/gaussauth-schema.sql` in the runtime image, so the SQL is generated from exactly the same migrations assembly as the binary. `scripts/generate-migration-script.sh` produces the same file locally.
- **Rationale**: Clarification Q1 (command in same image as default, SQL as alternative). No SDK on the production host (the runtime image has none). Credentials only via the same `ConnectionStrings__AuthenticationDatabase` environment variable/secret at run time; nothing embedded.
- **Alternatives**: EF migration bundle (self-contained executable) — works, but passes the connection on the command line (visible in process lists) and adds a second artifact to version; rejected. Separate admin CLI project — rejected as speculative.
- **Compose/deploy contract**: migrate runs first; API `depends_on` it with `condition: service_completed_successfully`; failure stops the rollout (FR-012c).

> **R4 verification result (T030, 2026-10-02):** the assumption that EF Core's per-call locking makes concurrent migrators safe was tested and **disproved** (2 of 3 rounds of two simultaneous `migrate` runs failed with `42704`/`2BP01`). The migrator therefore takes a PostgreSQL session advisory lock for the whole run (`pg_try_advisory_lock`, 5-minute wait, then category `locked`); with it, 3 of 3 rounds succeeded and a held lock is reported without touching the schema. Design-time SQL generation uses an `IDesignTimeDbContextFactory` so it needs no API settings; the generated file has its UTF-8 BOM stripped because `psql` rejects it.

### R5 — Health: keep liveness, add minimal readiness with the built-in health-check infrastructure
- **Decision**: `AddHealthChecks()` (shared framework, no package). `/health/live` remains the existing dependency-free 204. `/health/ready` runs two checks and returns **204 (ready) / 503 (not ready)** with an **empty body** (custom response writer, `ResultStatusCodes` override), so nothing can leak:
  1. *Database*: connection can be opened within a short timeout **and** no pending migrations (schema current). Pending/unreachable both → not-ready; the cause is logged server-side only, and only on state transitions to avoid log floods.
  2. *Profile storage*: root exists and a create/delete probe succeeds; unusable → not-ready.
  Results are cached briefly (a few seconds) so an open endpoint cannot be used to hammer PostgreSQL, while recovery is still observed within SC-006's 10 s.
- **Rationale**: FR-026–029, clarification Q2 (open, minimal, no probe credentials). Health endpoints are not rate-limited by named policies (orchestrator probes must not be locked out); the short cache is the abuse control.
- **Alternatives**: `AspNetCore.HealthChecks.NpgSql` / EF health-check packages — rejected (new dependency, constitution VII); JSON health reports — rejected (leak risk).

### R6 — HTTPS, HSTS, server header, CORS
- **Decision**: HSTS only for Production-class environments (it only emits on HTTPS requests, so it is effective once the trusted proxy forwards `https`). `UseHttpsRedirection` only when an explicit `HttpsRedirection:HttpsPort` is configured; otherwise it is skipped (TLS terminates at the proxy; the container listens on HTTP 8080). Kestrel `AddServerHeader = false`. CORS remains unconfigured (denied by default); a test asserts no `Access-Control-*` headers on simple and preflight requests, and documentation states that enabling browser access requires a future feature with an explicit allowlist.
- **Rationale**: FR-032/033, spec Assumptions (server-to-server).
- **Alternatives**: Add an optional allowlist now — rejected as speculative (spec: do not introduce unnecessary CORS).

### R7 — Rate limiting: validate, keep defaults, prove coverage
- **Decision**: Replace the inline `GetValue` block with a validated `RateLimitOptions` (per group: `PermitLimit ≥ 1`, `WindowSeconds ≥ 1`, bounded upper limits) using `IValidateOptions`. Keep the existing per-group defaults (they already differ by abuse profile) and document them. Add a coverage test that enumerates all endpoints and requires each to carry a named rate-limit policy or be on an explicit exempt list (`/health/*`) with rationale. Partition key stays the (post-forwarding) client address.
- **Rationale**: FR-035; "do not use one uniform limit". No behavior change apart from rejecting impossible values.

### R8 — Error handling and logging
- **Decision**: `SafeExceptionHandler` keeps its generic ProblemDetails 500 but logs the exception object server-side (structured, with the existing trace/correlation id). Add `appsettings.json` (levels: default Information, `Microsoft.AspNetCore` Warning, `Microsoft.EntityFrameworkCore` Warning, `Microsoft.Hosting.Lifetime` Information), `appsettings.Production.json` (built-in JSON console formatter with scopes, so `TraceId` is queryable), and `appsettings.Development.json` (more verbose). None contains secrets. EF sensitive-data logging stays off (verified by test). A startup summary log records environment and non-sensitive settings only; start/stop use hosting lifetime logs. A log-capture regression test runs the suite's sensitive scenarios and asserts no tokens/secrets/passwords/reset credentials/Authorization headers/file content appear.
- **Rationale**: FR-021, FR-030, FR-036–038. Reuses 009 correlation (`Activity` TraceId / `X-Correlation-Id`); no parallel tracing.
- **Alternatives**: Serilog/OpenTelemetry — rejected (no concrete requirement).

### R9 — Recovery delivery in Production (clarification Q5)
- **Decision**: Add `bool IsAvailable { get; }` to the existing `IRecoveryDelivery` port. `ProtectedFileRecoveryDelivery.IsAvailable` is true only in Development/Testing with a configured file. `RequestRecoveryAsync` returns **before** `GenerateResetCredentialAsync` when delivery is unavailable, so no credential is created, logged, audited or returned; the endpoint response is identical to today's generic response. Startup logs one structured warning when Production-class and unavailable. No new adapter is added; a future SMTP/webhook adapter implements the same interface.
- **Rationale**: FR-018a, spec edge cases. Smallest possible change that keeps the public contract and enumeration resistance.
- **Alternatives**: Separate "NotConfigured" adapter that throws (today's behavior) — rejected: still generates a credential and relies on exception flow.

### R10 — Profile storage persistence declaration (clarification Q4)
- **Decision**: New `ProfileImages:StorageIsPersistent` (bool). Production-class: missing → `StartupConfigurationException` naming the key; `true` → normal; `false` → start with a visible Warning that images may be lost on container replacement. The path is never inspected to guess persistence. `ProfileImages:RequirePersistenceDeclaration=true` opts other environments in. Readiness additionally checks the root is usable (R5).
- **Rationale**: FR-041.

### R11 — Data Protection key ring: mandatory persistent location in Production-class (release revision)
- **Decision**: `DataProtection:KeysPath` (absolute directory) is **required in Production-class** environments and optional in Development/Testing. Startup validation refuses to start when it is missing, relative, contains NUL, or cannot be created/written, with a Critical log naming only the key (never paths' contents, never key material). When valid, keys persist via the built-in file-system key store and a fixed application name isolates the ring. The service **cannot verify** that the directory survives container recreation and does not try to infer it from the path (same stance as the profile-storage declaration, clarification Q4); the operator is responsible, and the image, compose file and documentation make the volume explicit.
- **Why mandatory**: Identity's default token providers protect password-reset credentials with Data Protection. With the default ephemeral ring (per-container user profile), every restart or replacement invalidates outstanding reset credentials and replicas cannot validate each other's credentials. Persistence is required to preserve Identity password-reset credentials and any other Data Protection–protected state across restarts.
- **Key-ring sensitivity**: key files are key material. By default on Linux they are stored unencrypted at rest, so the directory is treated as secret-grade: owner-only permissions (`app` user), excluded from any broad or shared backup scope, and backed up only with the same care as other secrets. Encryption at rest (certificate/KMS protection) is out of scope and recorded as a documented limitation; the framework's "no XML encryptor configured" warning is therefore expected and documented rather than suppressed.
- **Alternatives**: Keys in PostgreSQL via the EF Data Protection package — rejected (new dependency + migration); keep it optional with a warning — rejected by the release requirement.

### R12 — Production image and evaluation composition
- **Decision**: Multi-stage `Dockerfile`: `sdk:10.0` restores/publishes (and generates the SQL script), `aspnet:10.0` runtime runs as the image's built-in non-root `app` user, `ENTRYPOINT ["dotnet","GaussAuth.Api.dll"]` in exec form (receives SIGTERM), `ASPNETCORE_ENVIRONMENT=Production`, `ASPNETCORE_HTTP_PORTS=8080`, writable `/data/profile-images` and `/data/keys` owned by `app` and declared as volumes. No secrets, no `.env`, no SDK. `compose.release.yml`: `postgres:17`, one-shot `migrate` service (`command: ["migrate"]`), `api` depending on it, named volumes for profile images, key ring and database, signing key via a mounted file (`Sessions__Signing__PrivateKeyPemFile`), `stop_grace_period` above the host shutdown timeout, `StorageIsPersistent=true`. `.env.release.example` holds placeholders only. `compose.dev.yml` and the AI development container are untouched. No container `HEALTHCHECK` (the runtime image has no HTTP client; orchestrators probe `/health/*`) — rejected alternative: a `healthcheck` subcommand (extra surface for little value).
- **Verification**: build the image, run it in compose against a clean PostgreSQL 17, upload an avatar, recreate the API container, confirm the avatar persists and readiness is green; confirm SkiaSharp loads in the runtime image (fall back to a different base only if it fails).
- **Alternatives**: Chiseled (shell-less) base — attractive for attack surface but unverified with Skia native assets; documented as an optional future tightening.

### R13 — Graceful shutdown
- **Decision**: Review rather than redesign. Set `HostOptions.ShutdownTimeout` explicitly (30 s) and give compose a larger `stop_grace_period`; the entrypoint is exec-form. Verify by test/review that profile writes use temp-then-move with cleanup on cancellation and that audited admin changes are transactional (a cancelled request leaves no partial state or file). Fix only if a defect is found (release-blocking category).
- **Rationale**: FR-039; spec avoids orchestration.

### R14 — Secret hygiene
- **Decision**: `scripts/scan-secrets.sh` scans tracked files and git history for private-key PEM headers, password-bearing connection strings that are not obvious placeholders, and long high-entropy assignments in config/compose/env-example files; `repositorySecretHygieneTests` runs a fast tracked-file subset in CI. `.env.release.example` uses `replace_with_*` placeholders like `.env.example`. Consumer secrets remain hash-only in config/DB (008/011); verified by existing `consumerCredentialTests` plus a log-capture assertion.
- **Alternatives**: Add gitleaks/trufflehog — rejected as new tooling; recorded as a recommended optional follow-up.

### R15 — Migration validation approach
- **Decision**: `releaseMigrationValidationTests` creates a **uniquely named empty database** on the test PostgreSQL 17 server (maintenance connection), applies the full chain via `Migrate`, asserts all 10 migrations applied in order, the expected unique constraints/indexes exist (normalized-email uniqueness, application-scoped role/permission uniqueness, membership uniqueness, consumer-credential per-application uniqueness, session/security-event indexes), boots the application against it, and drops it. An **upgrade test** migrates a second throwaway database only to `20261001202342_AddSecurityEvents` (the 009/010 schema), seeds representative data (users, applications, memberships, roles, the old audit permission with assignments, sessions, security events), migrates to latest, and asserts no row loss and that the audit permission is renamed with assignments intact. A failure-diagnostics test points the `migrate` command at an unreachable/invalid target and asserts non-zero exit with a value-free message. SQL-script equivalence (script applied to an empty database vs the command: same schema and history rows) is a scripted check in `quickstart.md`, run against the built image.
- **Rationale**: FR-007–013, SC-002/003.

### R16 — Migration safety review
- **Decision**: Record in `release-validation.md` an operation-by-operation table of each migration's `Up`. Pre-audit result: no table/column drops in any `Up`; one `DropIndex` (replaced index) in `AddRolesAndPermissions`; data SQL only in the two 011 migrations (permission seed — idempotent; audit-permission rename — assignment-preserving). Anything found destructive must be justified/documented or fixed; `Down` methods are reviewed but not part of the production path (rollback = restore from backup, documented).

### R17 — Consistency and regression review
- **Decision**: Run the entire existing suite in Release against clean PostgreSQL 17, then map each spec review bullet (users … admin operations) to a specific existing test or a recorded gap. Add a test only where a release-blocking category has no coverage. Review compiler warnings in Release for nullability, resource-lifetime, security and API-misuse categories; fix or justify each. Everything recorded in `release-validation.md`.

### R18 — Cryptographic configuration review
- **Decision**: Review-only unless a defect appears. Terminology fixed in all documentation: the access-credential **signing key is an asymmetric ECDSA key on the NIST P-256 curve (JWS algorithm ES256)**, loaded from PEM; its public half is published through the signing-keys endpoint. It is conceptually and operationally separate from the **symmetric, per-Application consumer secrets** (random high-entropy secrets stored only as one-way verifiable hashes, current/retiring rotation, 008/011). The two are never interchangeable and never share configuration. Implementation: .NET `ECDsa` + `Microsoft.IdentityModel` (no custom crypto); key size enforced; Production refuses ephemeral/dev key (already true; tests assert for Production-class names, not only the literal "Production"); issuer/audience/lifetimes read from the same options for issue and validate paths (test asserts a token issued with configured parameters validates, and parameter mismatch fails). Documented limitation: one active signing key, rotation requires a coordinated restart/redeploy (published key set has a single key).

### R19 — Documentation set
- **Decision**: Six operator documents under `docs/` (deployment, configuration reference, database, bootstrap, security baseline, limitations) covering every item in FR-043, each linking to the contracts here instead of duplicating them. Documentation includes the production rollout order (migrate → start → readiness), SQL-script alternative, backup/restore pairing of database and profile storage (consistent point-in-time guidance and what happens on mismatch), health exposure guidance (clarification Q2), proxy requirements (Q3), storage declaration (Q4), recovery-delivery limitation (Q5), consumer-secret rotation procedure the first-administrator bootstrap procedure, an explicit statement that an empty global administrator list means no global authority, key-ring persistence (required to preserve Identity password-reset credentials and any other Data Protection–protected state), and the known limitations list.

### R20 — Release-blocking triage
- **Decision**: `release-validation.md` keeps a findings table: id, area, category (release-blocking yes/no per spec list), disposition (fixed + test / documented limitation). Release-blocking items cannot be closed as "documented". Pre-identified candidates already tracked as tasks: recovery credential generation without a channel (R9), config-failure diagnostics (R2), readiness absence (R5).

### R21 — What is intentionally not done
No SMTP/webhook, HTTP bootstrap endpoint, CORS allowlist, key-rotation set, external observability, HA/load testing, container `HEALTHCHECK` subcommand, or additional endpoints beyond `/health/ready`.

### R22 — First global administrator bootstrap (release-blocking finding)
- **Finding**: `POST /users` and every other user operation require a global administrator (`RequireGlobalAdministrator`); a global administrator is a `UserId` listed in `Administration:GlobalAdministratorUserIds`; user ids are server-generated. On an empty database there is therefore no supported way to create the first user, so the list can never reference a real account. Tests inject their own policy; no documentation or command describes a production path. This breaks startup reliability and production configuration safety (spec release-blocking list) and so cannot be deferred as documentation.
- **Decision (confirmed with the project owner)**: a one-off `bootstrap-admin` command in the same image (`dotnet GaussAuth.Api.dll bootstrap-admin`, a minimal host like `migrate`). It reuses the existing create-user use case (email normalization, Identity password policy, profile fields), so no rule is duplicated or bypassed. Inputs: `Bootstrap__AdministratorEmail`, `Bootstrap__AdministratorPassword` *or* `Bootstrap__AdministratorPasswordFile` (mounted secret preferred), optional first/last name (defaults "Auth"/"Administrator"); never command-line arguments. Behavior: **refuses and changes nothing if any user exists** (so it cannot serve as a later backdoor); creates one active user; prints the new `UserId` and the exact configuration key to set; never prints or logs the password; records the same audit/log entries the use case already records. It grants **no authority**: authority exists only after the operator lists that id in `Administration:GlobalAdministratorUserIds` and restarts. An empty list still means no global authority (011 preserved), so a freshly migrated, unbootstrapped system is safe-by-default.
- **Operator procedure** (documented in `docs/bootstrap.md`): migrate → run `bootstrap-admin` → copy UserId → set `Administration__GlobalAdministratorUserIds__0` → restart API → authenticate as that user and call a global operation → remove the bootstrap password from the environment/secret.
- **Alternatives**: documented manual SQL insert — rejected (needs an Identity password hash produced outside the API; error-prone); configuration-driven auto-bootstrap at startup — rejected (secret-bearing, implicit, changes the 011 model); deferring to another feature — rejected (release cannot be operated).
